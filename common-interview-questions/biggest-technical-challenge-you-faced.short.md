The biggest technical challenge I've faced was rewriting a failing production WebSocket service, solo, in one month, with our company's first release on the line.

We run a real-time scoring platform, so live updates are the core product. During our pilot, the existing service — built on Django Channels and Redis — couldn't reliably hold even 500 concurrent users, connections kept dropping, and there was zero observability to explain why. The original developers were gone, the release was already scheduled, and I was assigned to fix it alone.

I mapped the system and found the real problems: each user was opening 6-7 separate WebSocket connections instead of one, the consumers were doing database work they shouldn't, and the whole stack was sync-first when it needed to be async. So I rewrote it on FastAPI, multiplexed all those connections into one per user — cutting total connections roughly 6x — stripped out the database calls so it only does Redis pub/sub fan-out, and added Prometheus, Loki, and Grafana so we'd have visibility going forward.

On the exact same EC2 instance, capacity went from around 500 unstable connections to over 3,000 stable ones, and the pilot and release moved forward on schedule. The biggest lesson: this should've been load-tested long before the pilot — since then, I treat load testing as a mandatory gate, not an afterthought.
